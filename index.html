START HERE / TOPIC 1

How Flutter talks to a backend.

Four building blocks. One clear contract between app and API.

FIRST MODULE
01
FOUNDATIONS · 8 MIN

REST: make a request, get a resource.

REST uses HTTP methods and resource URLs to give the Flutter app a predictable way to work with transactions.

Under the hood

Flutter sends a method, URL, headers and optional body. Express routes by method and path, runs middleware, calls a handler and returns an HTTP response. Requests are stateless: include required auth with each request.

NODE / EXPRESS
app.get("/api/v1/transactions", (_req, res) => {
  res.status(200).json({ data: [] });
});
FLUTTER / DART
final response = await http.get(
  Uri.parse('$baseUrl/api/v1/transactions'),
);
if (response.statusCode != 200) {
  throw Exception('Could not load');
}
Watch out for

Don't change server state with GET. Use resource names, keep secrets out of URLs, set client timeouts and handle network failures visibly.

Try it

Build GET and POST transaction routes; call GET from a Flutter repository and render the result.

Interview yourself
  1. What makes an API resource-oriented?
  2. Why is HTTP stateless?
  3. When should an API use POST rather than PATCH?
02
DATA SHAPES · 7 MIN

JSON: agree on the shape of a transaction.

JSON is the language-neutral format that TypeScript can serialize and Dart can parse into a typed model.

Under the hood

The API serializes an object to UTF-8 JSON. Flutter parses the bytes into dynamic values, then should map them at the boundary to a typed model. Treat every response as untrusted input.

NODE / TYPESCRIPT
res.json({ data: {
  id: "txn_123",
  amountMinor: 1299,
  currency: "USD",
  note: "Coffee",
} });
FLUTTER / DART
factory Transaction.fromJson(
  Map<String, dynamic> json,
) => Transaction(
  id: json['id'] as String,
  amountMinor: json['amountMinor'] as int,
  currency: json['currency'] as String,
);
Watch out for

Money should be integer minor units plus currency—not floating point. Use explicit UTC timestamps, parse into typed models and plan for new optional fields.

Try it

Define a transaction DTO with id, amountMinor, currency, occurredAt and nullable note. Parse and render it in Flutter; test a missing required field.

Interview yourself
  1. Why are floating-point amounts risky?
  2. Why parse JSON at an app boundary?
  3. How should an old client handle an unknown enum?
03
RELIABLE APIs · 7 MIN

Status codes: tell the client what happened.

A meaningful status and a consistent error body let the app respond correctly to invalid input, auth problems and server failures.

Under the hood

2xx indicates success, 4xx a request/client problem, 5xx an unexpected server issue. Network failures like DNS errors have no HTTP response and need their own handling.

NODE / EXPRESS
return res.status(400).json({
  error: {
    code: "INVALID_AMOUNT",
    message: "Amount must be positive",
  },
});
FLUTTER / DART
if (response.statusCode == 400) {
  throw const FormatException(
    'Check the transaction details',
  );
}
if (response.statusCode == 401) {
  // Follow the app's auth flow.
}
Watch out for

Use 201 for a created resource; don't hide errors in a 200 body. Never leak stack traces. Avoid blindly retrying POST requests that could duplicate writes.

Try it

Return a stable error code for invalid input. In Flutter, show a friendly validation message and distinguish an offline error.

Interview yourself
  1. What's the difference between 401 and 403?
  2. How is offline different from an HTTP error?
  3. Why might retrying POST duplicate a transaction?
04
SHARED CONTRACT · 10 MIN

OpenAPI: make the agreement visible.

A machine-readable API contract keeps mobile and backend development aligned, even when deployed clients lag behind the server.

Under the hood

OpenAPI describes endpoints, schemas and responses; tooling can generate docs or client types. The specification alone doesn't validate runtime data: tests and server validation still matter.

OPENAPI / YAML
paths:
  /api/v1/transactions:
    get:
      responses:
        "200":
          description: Transactions loaded
          content:
            application/json:
              schema:
                type: object
FLUTTER / REPOSITORY
final response = await client.get(uri);
if (response.statusCode != 200) {
  throw ApiException.fromResponse(response);
}
final body = jsonDecode(response.body);
return parseTransactions(body);
Watch out for

Document nullability, errors and dates—not just URLs. Prefer additive compatible changes. Generated types don't replace validation or integration tests.

Try it

Specify GET and POST transactions, input validation and errors in OpenAPI. Test Express and the Flutter repository against the contract.

Interview yourself
  1. What does OpenAPI provide beyond docs?
  2. Which changes preserve compatibility with old clients?
  3. Why do generated types not replace server validation?

KEEP THIS CLOSE

Flutter cheat sheet.

Everyday patterns for layouts, async work, models, and running your app.

▤
LAYOUT

Give a Row child room to behave.

Constrain flexible text to the remaining width so it cannot push its siblings off screen.

Row(
  children: [
    const Icon(Icons.receipt),
    const SizedBox(width: 8),
    Expanded(
      child: Text(
        title,
        maxLines: 1,
        overflow: TextOverflow.ellipsis,
      ),
    ),
    const Icon(Icons.chevron_right),
  ],
)
Use Flexible if the child may be smaller without filling all remaining space.
⌁
ASYNC + LIFECYCLE

Await safely before using context.

Check that the widget still exists after an async gap before navigation or showing UI.

Future<void> save() async {
  await repository.save(item);
  if (!mounted) return;
  ScaffoldMessenger.of(context)
      .showSnackBar(
        const SnackBar(content: Text('Saved')),
      );
}
In a State object use mounted; with a recent Flutter BuildContext, use context.mounted.
⌘
DATA MODEL

Parse JSON at the boundary.

Turn untrusted decoded JSON into typed data once, rather than spreading dynamic through widgets.

class Expense {
  const Expense({
    required this.id,
    required this.amountMinor,
  });

  final String id;
  final int amountMinor;

  factory Expense.fromJson(
    Map<String, dynamic> json,
  ) => Expense(
    id: json['id'] as String,
    amountMinor: json['amountMinor'] as int,
  );
}
Store money as integer minor units with an explicit currency; format it only for display.
◷
ASYNC UI

Render every Future state.

A FutureBuilder is useful for a one-off future; create and retain the future outside build.

FutureBuilder<List<Expense>>(
  future: expensesFuture,
  builder: (context, snapshot) {
    if (snapshot.hasError) {
      return const ErrorView();
    }
    if (!snapshot.hasData) {
      return const CircularProgressIndicator();
    }
    final expenses = snapshot.data!;
    if (expenses.isEmpty) {
      return const EmptyExpensesView();
    }
    return ExpenseList(expenses: expenses);
  },
)
For interactive or shared app state, prefer your chosen state-management pattern.

NAVIGATION

Push a screen; return a result.

The built-in Navigator is handy for a small example. Use the app's router for real route policy and deep links.

final result = await Navigator.push<bool>(
  context,
  MaterialPageRoute(
    builder: (_) => const EditExpensePage(),
  ),
);

if (!context.mounted) return;
if (result == true) refreshExpenses();
Use named, typed routes in the routing solution your app has adopted; don't scatter navigation rules through widgets.
FIELD NOTES / BEFORE YOU SHIP

Important points for building Flutter apps.

Small decisions that keep an app maintainable, testable, and kind to its users.

01

Organize by feature.

Keep screens, state, models, and data access for a feature together. Introduce abstraction when it clarifies a boundary, not just to add layers.

features/expenses/{data,domain,presentation}
02

Choose state deliberately.

Use setState for local ephemeral UI state. Adopt Provider, Riverpod, or Bloc when sharing state or coordinating app behavior needs it.

DON'T ADD GLOBAL STATE BY DEFAULT
03

Separate app environments.

Use explicit dev, staging, and production configuration. A value bundled in a mobile app is not a secret—keep private keys on the server.

CONFIGURE, DON'T HARDCODE
04

Dispose what you own.

Dispose controllers and animation controllers; cancel subscriptions and timers when their owner is disposed.

@override
void dispose() {
  controller.dispose();
  super.dispose();
}
05

Build for real people.

Support text scaling, screen readers, contrast, localization, and comfortable touch targets. Avoid color as the only signal.

CHECK ACCESSIBILITY ON DEVICE
06

Test behavior, not implementation.

Unit-test business rules; widget-test loading, empty, error, and success states; integration-test important end-to-end flows.

TEST THE FAILURE PATH, TOO
07

Measure before optimizing.

Profile in a profile or release build. Use lazy lists for long collections and DevTools to investigate rebuilds and memory.

DEVTOOLS → PERFORMANCE + MEMORY
08

Make failures diagnosable.

Show useful recovery guidance, report unexpected errors, and remove personal or financial data from logs and crash reports.

OBSERVE WITHOUT LEAKING DATA
✳

Fintech reminder Never trust values from the app for authorization or balances. Validate every operation on the server, store tokens securely, and avoid logging credentials or transaction details.

BEFORE YOU CALL IT DONE

Keep in mind while developing.

A working screen is the start. Build with constraints, failure states, and the next person who has to maintain it in mind.

Jump to layout essentials ↓
▤

Layout follows constraints.

Flutter constraints flow down, sizes flow up, and parents position children. Reason from the parent before tweaking the child.

  • ✓Give flexible Row content finite width. In a bounded Column, use crossAxisAlignment: CrossAxisAlignment.stretch when children should fill its available width.
  • ✓Wrap long text in Expanded or Flexible inside a Row; choose wrapping or ellipsis intentionally.
  • ✓Use scrollable content when it may exceed available height. Avoid Expanded in an unbounded scroll direction.
  • ✓Use LayoutBuilder for local parent constraints—not fixed device widths.
ROW INSIDE A BOUNDED COLUMN
Column(
  crossAxisAlignment: CrossAxisAlignment.stretch,
  children: [
    Row(
      children: [
        const Icon(Icons.receipt_long),
        const SizedBox(width: 8),
        Expanded(
          child: Text(
            transaction.merchant,
            maxLines: 1,
            overflow: TextOverflow.ellipsis,
          ),
        ),
        Text(transaction.formattedAmount),
      ],
    ),
  ],
)

Why this works: the column fills its bounded width; Expanded gives the merchant text only the remaining horizontal space. If the parent gives the column unbounded width, constrain that first.

◈

State and lifecycle stay predictable.

  • ✓Keep build fast and side-effect free; start I/O from a lifecycle or state layer.
  • ✓Place state at the lowest common ancestor that needs it. Separate transient UI state from server state.
  • ✓After an await, check context.mounted before using context to navigate or show UI.
  • ✓Use keys when identity matters, such as reordered stateful list items—not everywhere by default.
⌁

Treat the network as unreliable.

  • ✓Keep HTTP behind a repository or client boundary, not inside widget build methods.
  • ✓Represent loading, success, empty, and failure states explicitly.
  • ✓Set request timeouts; handle HTTP errors separately from offline and transport failures.
  • ✓Don't retry non-idempotent writes blindly; protect against duplicate transactions.
  • ✓Keep secrets out of the app; validate inputs on the server too.
◎

Review like a user—and like an engineer.

  • ✓Test narrow screens, large text, long names, empty lists, loading and failures.
  • ✓Check accessibility labels, contrast, tap targets, keyboard and focus behavior.
  • ✓Run formatter, analyzer, and targeted tests; check there are no overflow or unbounded-flex exceptions.
  • ✓Make sure API field names, nullability, codes, and errors agree with the contract.
DON'T SHIP THESE SHORTCUTS

Don't assume a Row wraps. Don't hardcode screen widths. Don't silence overflow warnings without deciding how content adapts. Don't trust client validation as security.
